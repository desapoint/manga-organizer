# Pre-upgrade backup and recovery

F54 requires a verified pre-upgrade backup before an existing installation applies pending migrations or any other incompatible persistent-data change. This is the first implementation slice. No new identity or release schema reaches existing data before this guard and a rehearsed restore path. [Backlog](EXPANDED-BACKLOG.md)

## Current state and snapshot scope

At the PR #30 baseline, both startup and `--migrate` call `DatabaseMigrations.Apply` in `Program.cs`. It checks numbered migration history and applies the missing scripts in one SQLite transaction. There is no pre-upgrade backup gate. The main file is `organizer.sqlite`. The owner identity/password verifier, catalog, root settings, metadata, progress, edition and operation records live there. ASP.NET data protection keys are in `keys/`. `CoverCache` stores cached artwork separately in `cover-cache.sqlite` and uses WAL. `file-recovery` and media-root staging/quarantine may hold actual media bytes.

Each backup includes the consistent main database and needed data-directory configuration and identity key material. Inventory any externally injected settings and secrets needed to restart, with their restore instructions and protected location. Validate a documented artwork-cache rebuild from accessible media or include a consistent cache snapshot when needed to preserve authoritative artwork data. Future release facts, preferences, duplicate decisions, trash and journal state enter the database backup automatically. Snapshot the operation sequence and references to media recovery material. Explicitly describe which bytes require separate media backup. Never copy secrets into a manifest or logs.

## Snapshot and verification

- Detect fresh install, current schema, incompatible future history and known pending migrations before the first persistent upgrade write. Reuse the history rules in `DatabaseMigrations`. A fresh install and an already current schema need no pre-upgrade snapshot. Validate supported legacy databases that predate the ledger. Both entry points share the same admission path.
- Acquire a data-directory upgrade/exclusive writer fence across startup, manual migrations and restore. Coordinate with SQLite writers and journaled file operations. A competing instance or unreconciled operation fails safely or enters a documented maintenance path. Recheck the source schema and operation sequence before migration. Take separate database/config snapshots only with a common fenced state.
- Use SQLite's consistent backup mechanism through the existing provider. Include committed WAL state through SQLite and verify it with a WAL fixture. Avoid relying on a bare copy of the main file or taking an ordinary file copy of mutable key/config files without a fence. Use a protected staging directory on a qualified filesystem, require sufficient space and atomic no-clobber publication, and make the backup durable before declaring it verified.
- Reopen the staged database read-only. Check integrity, foreign keys where applicable, schema ledger, identity and critical table counts against the snapshot inventory. Hash included files and verify the manifest before publishing. Include application version/build, schema and compatible restore version, UTC timestamp, restoration instructions, result, file inventory and backup location. Audit success without exposing secrets. On any required backup or verification failure stop before migration, retain a diagnostic for the operator, and keep the original database available to the old version.
- Restrict access to the server/operator. Verify Windows ACLs and Docker UID/GID and directory modes. Reject unsafe links and unapproved backup locations. Support configurable backup retention independent of F34 trash expiration. Retire older verified backups only after publishing a good replacement. Decide default backup retention and whether to support optional encryption through operator-policy research. Keep manual backups and protected snapshots out of automatic retention unless explicitly included.

## Restore rehearsal and media reconciliation

Stop the server and take or retain a verified snapshot of the failed/current state. Review compatibility and verify hashes and integrity again. Stage an offline restore to a separate directory, replace the data directory under the same fence, avoid stale WAL sidecars, restore needed keys and owner settings with restrictive access, and start the matching application version. Verify catalog, roots, owner identity, progress, edition and preferences, and file-operation/trash references. Document cache restoration or rebuild and the circumstances that require signing in again. Preserve the pre-restore copy until the operator approves retirement.

Database restore can recreate references to a file moved or purged after the snapshot. Freeze managed writes and trash expiration until the journal and storage reconcile against the restored snapshot position. Reconcile each path with current verified bytes and mount identity, then use separately retained trash/recovery copies or the operator's media backup where applicable. A database backup cannot recreate purged media. Preserve tombstones and report unavailable content instead of replaying stale removals. Test original-path conflicts and an operation after the snapshot, along with failed backup, legacy upgrade, restart and restore of the matching old binary. Qualify the data-directory lock and durable publishing on Windows and Docker and rehearse the media reconciliation on a real Unraid share. [Acceptance A24–A28](EXPANDED-ACCEPTANCE.md)

## Packaged startup guard

Stop the running server before installing an update or invoking the packaged `--migrate` command. Startup and `--migrate` hold the same data-directory lease. A running version that predates the lease still needs to be stopped during the upgrade. If a pending migration finds an interrupted or review-required file operation, resolve it in the previous server before restarting the upgrade.

An upgrade with pending migrations creates a verified snapshot in `upgrade-backups` under the server data directory. The folder contains `organizer.sqlite`, existing ASP.NET key XML files, and `manifest.json` with schema versions, record counts and file checksums. Keep the folder private to the server or recovery operator. The server retains snapshots for manual management. Backup creation failure aborts migration. Fresh and already current databases skip snapshot creation.

To rehearse a database restore, verify the saved checksums and SQLite integrity, then copy the database and keys into a separate offline data directory. Reuse the former deployment's external configuration and binary, and avoid copying WAL sidecars into the staged directory. Check the saved identity, library metadata and progress before switching data directories. Keep the original media and recovery paths available, and reconcile journaled file operations before using restored data for file management. The verified snapshot covers database and key state. The cover cache can be rebuilt during scanning.
