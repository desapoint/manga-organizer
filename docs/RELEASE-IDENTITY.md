# Canonical chapters and release metadata

This specification owns chapter identity, edition membership, release metadata and their migration. F03 and F04 cover these changes. F05 covers bulk release correction. The names below describe proposed records. The implementation can adapt them to the existing SQLite store.

## Identities and relationships

| Record | Key and responsibility |
| --- | --- |
| Work | Stable server-owned work ID. Link existing series groups and reviewed provider IDs as aliases. Provider rematches or root changes preserve the work ID. Title matches alone do not join works. |
| Canonical chapter | Opaque stable ID scoped to a work. Store display label, structured number and part when applicable, kind, and explicit order. Use exact decimal normalization and comparison. Support named extras, prologues, epilogues and bonus content without assigning them synthetic numeric identities. A display label may occur on multiple distinct chapters. |
| Publication edition and label mapping | Give each edition its own volume definitions and numbering scheme. Keep source namespace, source label or stable external ID, edition, volume context if relevant, and mapping evidence. Map each resolved source reference to a chapter ID. Model volume membership as an ordered relationship to chapters. Different editions can place the same chapter in different volumes. |
| Release | Stable ID for a published, translated, scanned or modified variant of one work. Link edition and source identities when known. Store a release version and revisions independently of a file path. |
| Release asset and coverage | Link the release to one or more content identities. Link each asset to the chapters it contains and retain ordering and coverage evidence. This supports standalone chapters, volumes, omnibuses, multi-volume files, and collections with non-consecutive chapters. An unresolved link retains its source labels and evidence. |
| Content and file location | Reuse `library_content` for whole-file SHA-256 and `library_file` for authorized root, path and availability. Record physical object identity separately where proven. Exact copies can share content across paths. One content identity may carry several release associations when review warrants it. Neither similarity nor a path change makes a new content identity. |
| Completion and preferred release | Track chapter state per owner and canonical chapter. Persist preferred release separately from current-session choice. Preserve the existing per-content page resume and revision. [Reading continuity](READING-CONTINUITY.md) |

Chapter 25 can have one ID across translated, censored, uncensored, color, black-and-white, standalone and omnibus releases. A verified absolute numbering scheme can map chapter 25 directly. An edition that resets at each volume needs a scoped mapping. Chapter 1 in two volumes is kept unresolved or mapped to separate logical chapters until evidence proves the relationship. Named extras may need manually chosen order and identity. Review disagreements among sources and retain the original claims.

## Release attributes and evidence

| Attribute group | Fields and treatment |
| --- | --- |
| Language and translation | Use normalized tags for release languages and original publication language as separate fields. Allow multiple release languages or an explicit unknown state. Track official, unofficial or fan translation, group, translator and publisher when known. |
| Edition and content | Store publication edition and original, digital, print-scan, revised or other release type. Track black-and-white, full-color, partially colored or unknown separately from censored, uncensored, mixed or unknown. Track revised translations, corrections, bonus content, extras and labels such as v1 or v2. Several attributes coexist on one release. |
| Technical properties | Record content hash, archive format, size, page count and the evidence for each. Track per-page image formats and dimensions or a derived summary, resolution and quality indicators, archive compression, readability, integrity and missing, unreadable or corrupt pages. Optional ordered page fingerprints belong to a content version. Keep chapter and volume coverage as links. File properties that depend on bytes belong to content or release assets. Preserve conflicting counts such as ComicInfo's declared count and indexed image entries. |
| Provenance | Preserve original filename, acquisition source, source-specific manga and chapter IDs, provider IDs, embedded metadata, discovery and import timestamps, and evidence confidence. Keep the original filename after moves. Store manual overrides separately from extracted values. |

Model evidence as assertions indexed by subject and field. Each assertion records source kind and reference, observed value, extractor version where applicable, observation time, confidence and review disposition. The resolved field exposes verified, inferred, manual, conflicting or unknown. New evidence can update a resolved automatic field or surface a conflict. An explicit owner override, including clearing a value, takes precedence until the owner resets it. Preserve disputed and replaced evidence for review. Do not require metadata to index or open a supported file. Bulk correction previews fields, selected releases and locked overrides, applies the selected edits in one transaction and records per-release results. The duplicate workflow uses the same editor and persistence.

Reuse filename grouping and chapter hints, `ComicInfoXml`, archive directory enumeration, cached covers, reader manifests and existing metadata links. Start with known naming conventions, directory and scanlation tags, explicit language tags, bounded ComicInfo, chapter folders and page filenames. Record what is declared versus observed in content. Evaluate other archive metadata, embedded PDF or EPUB fields on their supported decoders, existing provider facts, acquisition provenance and optional image-property analysis as subsequent extractors. Test contradictory tags, malformed XML, low confidence, mixed releases and rescans with an owner lock. Acquisition stays on its existing schedule. [Provider and boundary research](READING-CONTINUITY.md#evidence-and-research)

## Migration and compatibility

`0011` stores inferred coverage by content, `0012` adds edition manifests and keys completion by owner, work, volume and chapter, and `0014` stores a content preference with the same legacy scope. `LibraryStore.Editions.cs` uses a metadata work key or a local root and series key. `content_chapter` provides reviewed assignments. The existing on-disk reader position is keyed by owner and content.

1. Ship the verified pre-upgrade backup and restore path first. Keep applied numbered SQL migrations immutable and record subsequent changes in the existing migration ledger. [Upgrade recovery](UPGRADE-RECOVERY.md)
2. Add work and chapter IDs and reviewed mapping tables alongside existing rows. Walk explicit assignments, legacy work keys, inferred coverage, edition manifests, completion and preferences. Preserve each original reference in a migration crosswalk with its provenance. Resolve work aliases only via reviewed identifiers. Backfill resolved absolute chapter IDs only when numbering and edition evidence support a unique match. For unresolved tuples retain separate provisional IDs or unresolved links with their legacy scope and original state. Retry backfill by stable legacy keys and record completed checkpoints. Preserve files that lack metadata and avoid rescanning media as a migration prerequisite.
3. Keep old chapter URLs and reader contracts translating through the crosswalk while clients move to IDs. During the compatibility window keep reads and writes coherent in one transaction or behind one translation layer. Do not fork completion or preference writers. Preserve a per-content resume entry exactly. Preserve legacy explicit completion and preferred content IDs even if a mapping is pending or its file is unavailable. If several legacy rows converge with conflicting choices or completion, expose the conflicting records for owner resolution rather than fabricating recency, marking additional chapters complete or overwriting explicit preferences.
4. Backfill release and asset associations additively using known metadata, content and original paths. Preserve legacy sources, paths and content hashes. A manual mapping correction updates references with a preview of affected state and records redirects or superseded links. If the reassignment is ambiguous, keep the source progress and release history pending review. Replay scan, move and correction tests during cutover. Remove legacy writers only after reference and progress parity, tested backup restore, and client compatibility checks. A downgrade after schema activation uses the version-matched backup and media reconciliation. [Acceptance A01, A02 and A24](EXPANDED-ACCEPTANCE.md)
